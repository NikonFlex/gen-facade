# Метрики и проверки корректности

Обновлено: 2026-09-25

ТЗ требует оценку по пяти группам метрик и отдельно — автоматические проверки
геометрической корректности. Это один из немногих пунктов ТЗ, сформулированных
конкретно, поэтому на защите спросят обязательно.

Пока ничего не выбрано — файл задаёт рамку, которую надо наполнить.

## Пять групп из ТЗ

### 1. Визуальное сходство
Насколько сгенерированный фасад похож на настоящие.
Кандидаты: FID, KID, LPIPS по растеризованному SVG; попиксельный MSE/IoU при сравнении
векторизации с исходным растром. Не выбрано.

### 2. Корректность геометрии
Нет самопересечений, замкнутые контуры, элементы не выходят за границы фасада,
не перекрываются недопустимым образом, линии параллельны/перпендикулярны где должны.
Считается прямо по SVG, без обучения. Не выбрано.

### 3. Корректность структуры
Самое важное для нашей гипотезы вклада (см. [methods.md](methods.md)):
регулярность сетки этажей, выравнивание элементов по вертикальным осям, одинаковость
размеров однотипных элементов, соответствие числа этажей и элементов заданному условию.
**Готовых метрик, скорее всего, нет — возможно, их придётся предложить самим.**
Это само по себе может быть частью научного вклада.

### 4. Разнообразие
Чтобы модель не выдавала один и тот же фасад. Кандидаты: внутренняя вариативность
выборки, recall/coverage в дополнение к FID. Не выбрано.

### 5. Доля валидных векторных документов
Процент выходов, которые парсятся как корректный SVG и открываются в целевом
редакторе/CAD. Самая простая в реализации метрика, стоит сделать первой —
она же служит smoke-тестом пайплайна.

## Автоматические проверки геометрической корректности

Отдельный пункт ТЗ. По сути — валидатор, который принимает SVG и выдаёт список
нарушений. Черновой набор правил:

- [ ] SVG парсится, все элементы имеют валидные координаты
- [ ] контуры замкнуты, нет самопересечений
- [ ] все элементы внутри габаритов фасада
- [ ] окна/двери не пересекаются друг с другом
- [ ] элементы одного класса на одном этаже имеют одинаковый размер (с допуском)
- [ ] элементы выровнены по вертикальным осям (с допуском)
- [ ] шаг между этажами постоянен (с допуском)
- [ ] число этажей и элементов соответствует условию генерации

Допуски надо будет обосновать — либо из разметки реальных фасадов, либо экспертно.

## SVD-метрика регулярности: что это и откуда

Линия работ: **Yang et al., «Parsing façade with rank-one approximation»,
CVPR 2012** → **Pro-DG** (`10.1111/cgf.70487`) → **Beyond Segmentation**
(EUROGRAPHICS 2026 Short, arXiv:2604.09260, DOI `10.2312/egs.20261020`).

Важно для обзора: это **две разные метрики**. Pro-DG определяет попарное
расстояние структурной сложности `D_SVD(A,B,ε)` для сопоставления регионов
при редактировании. Beyond Segmentation взял идею и определил **другой скаляр**,
без ε и без пары — как оценку качества. Ссылки в обзоре нужны разные.

**Что считает BSeg** `[проверено: полный текст + код]`: бинарная маска
**одного класса** (по умолчанию `window`) растеризуется из боксов, раскладывается
по SVD, счёт — сумма MSE между маской и её rank-k приближениями для k = 1..25.
Меньше = регулярнее.

**Замкнутая форма** (выведена из формулы Pro-DG, избавляет от цикла и от их кода):

```
score(A) = (1/MN) · Σ_{i≥2} min(i−1, K) · σ_i²        (σ в шкале 0..1)
```

то есть это **взвешенная энергия неведущих сингулярных направлений**.
Совпадение с прямым циклом проверено до машинной точности.

## ⚠ Оптимум метрики вырожден — наш собственный результат

`[проверено: своя реализация, tools/svd_metric_probe.py]`

| маска | score | белых пикселей |
|---|---|---|
| идеальная решётка 5×6 | **0.00000** | 13.7% |
| идеальная решётка 12×14 | **0.00000** | 69.9% |
| **один ряд окон** | **0.00000** | 2.7% |
| **один большой прямоугольник** | **0.00000** | 23.8% |
| **пустая маска, ничего не сгенерировано** | **0.00000** | 0% |
| решётка + витрина первого этажа | 0.03963 | 22.4% |
| джиттер ±3 px | 0.04568 | 13.7% |
| джиттер ±10 px | 0.16287 | 13.7% |

Причина алгебраическая: маска идеальной осевой решётки — внешнее произведение
индикатора строк на индикатор столбцов, то есть матрица **ранга 1**, и все σ_i
при i ≥ 2 равны нулю. Пустая маска и один прямоугольник — тоже ранг ≤ 1.

**Метрика конфаундится с полнотой.** Прогон «джиттер 5 px × доля выброшенных»:

| выброшено элементов | score |
|---|---|
| 0% | 0.0891 |
| 50% | 0.0485 |
| 75% | 0.0154 |
| **90%** | **0.0000** |

То есть **выбросить девять окон из десяти выгоднее, чем выровнять их**.
Сами авторы признают в §5, что при большом весе лосса «it can sometimes lead
to missed detections», но контроля на recall в статье нет.

Три следствия: метрика **поощряет недогенерацию**, **поощряет mode collapse**
(модель, всегда выдающая одну решётку, получает идеальный ноль) и **штрафует
легитимную архитектуру** — витрина первого этажа (0.040) штрафуется на том же
уровне, что решётка с трёхпиксельным джиттером (0.046).

**Это самостоятельный методологический результат**, годный в текст ВКР
и потенциально в статью. Воспроизводится одной командой.

## Брать ли её

**Да, но только как вспомогательную колонку**, и с оговорками: считать в паре
с числом элементов и recall, иначе улучшение нечитаемо; по нескольким классам,
а не только window; при фиксированном разрешении растеризации; **никогда
не оптимизировать под неё напрямую**.

Плюс от включения реальный: это единственная точка сравнения с существующей
работой по фасадам, и она закрывает вопрос «почему вы не сравнились
с Beyond Segmentation».

**Реализовать самим** по формулам из статьи — она под CC BY 4.0, формул
достаточно. Их код трогать нельзя: **LICENSE в репозитории нет**, а патч лосса
производен от `ultralytics` под **AGPL-3.0**.

## Alignment loss: статья и код расходятся

`[проверено: полный текст + код]` В статье напечатан **L1** (модуль разностей),
в коде — **L2²** (квадраты). И «боксы не перекрываются» в статье означает IoU ≈ 0,
а в коде — строгую дизъюнктность интервалов по другой оси. Если будем
воспроизводить, это надо знать.

Гиперпараметры: порог `T` **в абсолютных пикселях** (зависимость от разрешения),
вес `W`. Дефолт `T=9, W=0.5`. Чисел в статье нет вообще, только три графика.

## Что остаётся нашим вкладом

Новую формулировку — составную, каждая часть проверяема:

> Существующие метрики структурной регулярности фасадов немногочисленны и все
> происходят либо из одной линии работ (Yang 2012 → Pro-DG → Beyond Segmentation),
> либо из архитектурных журналов (Nexus Network Journal). При этом **все они
> растровые**, ни одна не работает на векторном представлении; все применялись
> к **парсингу, редактированию или анализу**, ни одна — к оценке генерации;
> ни одна не связана с **текстовым условием**; а единственная reference-free
> из них имеет **вырожденный оптимум** и конфаундится с полнотой, что мы
> показываем количественно.

**Внешнее подтверждение пробела** `[проверено: grep по полному тексту]`:
в обзоре *Computer-Aided Layout Generation for Building Design: A Review*
(arXiv:2504.09694, 2025) слова `regularity`, `symmetry`, `SVD`,
`constraint violation` встречаются **ноль раз**. Разделы про метрики там —
«Fidelity and diversity» (FID, KID, SCA, KL) и «Graph constraint metrics».

## ⚠ Прецедент, от которого надо отстроиться

**GSDiff** (arXiv:2408.16258, AAAI 2025) — генерация **векторных** планировок
с alignment loss и reference-free метрикой **AE (Alignment Error)** рядом с FID/KID.
То есть связка «alignment loss + метрика выравнивания для векторной архитектурной
генерации» **уже сделана — для планов**. Наша новизна должна проходить
по фасадам и тексту, а не по «alignment loss вообще». `[из отчёта агента]`

## Соответствие описанию: изобретать не надо

Есть три готовых шаблона, и все сводятся к одному: из текста извлекаются
проверяемые требования → каждое проверяется детерминированным предикатом →
метрика есть доля выполненных.

- **CADTests** (arXiv:2605.07807) — исполняемые тесты по промпту, эталон не нужен
- **SceneEval** (arXiv:2503.14756, WACV 2026 Oral) — VLM только отображает
  формулировку на закрытый список типов, сама проверка геометрическая
- **GenEval / VPEval / DSG** — «все требования выполнены → 1», с разбивкой
  по навыкам и DAG зависимостей между вопросами

**Где здесь наша новизна.** Во всех этих работах «ответчик» — шумный детектор
или VQA-модель по растру, и именно на счёте и пространственных отношениях они
ошибаются (задокументировано в SVGEval, arXiv:2608.01977, и SVG-Score,
arXiv:2609.03806). У нас выход **векторный**, поэтому ответчиком становится
**парсер**: подсчёт окон, «окно внутри полигона стены», «колонна выровнена
с точностью ε», «этажей ровно N» — точные проверки, а не вероятностные.

Формулировка для защиты: *переносим схему проверяемых требований из text-to-CAD
и text-to-scene на векторные фасады, заменяя нейросетевой ответчик точным
парсером, что делает метрику детерминированной и воспроизводимой.*
