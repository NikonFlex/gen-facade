https://github.com/ranjian0/building_tools · **MIT** (проверено по файлу LICENSE) ·

**Проверено прогоном лично** (Blender 4.0.2, headless): план 9×11, два этажа,
окна, дверь, балкон, двускатная крыша — отрабатывает. На выходе
классифицированные прямоугольники с координатами в метрах:

```
{'cls':'window', 'xy':[-4.35,-4.35, -5.05,-4.01], 'z':[1.13,2.37]}
{'cls':'door',   'xy':[ 4.35, 4.35, -0.42, 0.42], 'z':[0.20,2.22]}
```

Окна одной стены лежат в одной плоскости — перевод в 2D-фасад и SVG тривиален.
Скорость ~1.2 с на здание: 10 000 домов ≈ 3.5 часа однопоточно.
Крыши FLAT / GABLE / HIP, то есть коттеджи покрыты.

Что сделать:
- форк под MIT и обёртка на ~50 строк, обходящая три известных подвоха:
  `api/options.py` падает на Python ≥3.11 (mutable defaults);
  декоратор `@crash_safe` роняет Blender в `--background` через попап;
  `create_window/door/roof` требуют режима EDIT_MESH, но сами в него не переходят;
- рандомизатор планировок и разметки фасада;
- экспортёр в SVG + JSON;
- добавить недостающие классы: **карниз** (ближайшее `ROOF_HANGS`) и **отлив**.

Нужен при любом выборе домена — это источник предобучения для варианта 2
(свой трансформер), см. gf#10.

Готово, когда: одной командой генерируется N домов, на каждый есть SVG-чертёж
и JSON со списком элементов, выборочные результаты проверены глазами.

## Что установлено: есть второй путь, возможно лучше

**IFC → семантический SVG-фасад работает** `[проверено: артефакты прогона агента
осмотрены лично]`. Команда:

```
IfcConvert дом.ifc out.svg --auto-elevation --scale 1:100 \
    --exclude entities IfcOpeningElement --svg-segment-projection -y
```

На FZK-Haus (реальный одноквартирный дом KIT) выдаёт четыре вида
Elevation East/North/South/West и **классифицированные прямоугольники
в настоящих метрах**:

```
IfcWindow  EG-Fenster-8   x=6.50  y=-2.00  w=2.00  h=1.20
IfcDoor    Haustuer       x=-5.50 y=-2.01  w=1.01  h=2.01
IfcSlab    Dach-1         x=-10.50 y=-6.32 w=5.50  h=3.41
```

Проверил сам: в выходных SVG 41 группа `projection IfcWindow`,
14 `IfcDoor`, 14 `IfcSlab`, в `structure.json` 103 элемента. Внутренние двери
на фасад корректно не попадают.

Три грабли, обойдены в скрипте агента (`scratchpad/cad/ifc/ifc2facade.py`):
`--auto-elevation` в одиночку даёт **пустой файл** (нужен `--exclude entities
IfcOpeningElement`); `--svg-without-storeys` ломает вывод; **без
`--svg-segment-projection` семантики нет вообще** — только безымянные пути.
Python API `ifcopenshell.draw` не заменяет CLI: поля `segment_projection` в нём нет.

Лицензия IfcConvert — **LGPL-3.0-or-later** (в корне лежат и `COPYING`, и
`COPYING.LESSER`, GitHub показывает GPL-3 — это про Bonsai). Как внешний бинарь
LGPL наш код не заражает.

**Чем этот путь лучше building_tools:** классы приходят из настоящей
архитектурной семантики IFC, а `data-guid` позволяет подтянуть к прямоугольнику
все свойства элемента (проверено: `OverallWidth=2.0, OverallHeight=1.2` сходится
с bbox). То есть ground truth получается детерминированно, без разметки и её шума.

**Чем хуже:** открытых IFC-моделей жилых домов **всего порядка 9**, из них
настоящих коттеджей 5–6. На обучение не хватит — это held-out для валидации.

**Вывод для этой задачи:** вероятно, правильная связка — не «building_tools →
SVG», а **свой процедурный генератор поверх `ifcopenshell.api` → IfcConvert →
размеченный SVG**. Объём даёт генератор, реальные 9 моделей уходят в held-out.
Кандидат на основу генератора — `hypar-io/Elements` (MIT, 418★), внутрь никто
не смотрел.

Отдельно: **открытого процедурного генератора зданий в IFC не существует**
(проверено поиском по GitHub) — то есть это самостоятельный вклад, а не костыль.

## Тупики

- DWG закрыт: LibreDWG — GPL-3 (вирусный), ODA File Converter — non-commercial.
  Работать в **DXF** через `ezdxf` (MIT, живой).
- Не строить цепочку `структура → DXF → SVG`: штатный `SVGBackend` в ezdxf
  **теряет имена слоёв**, группируя пути по цвету. Финальный SVG писать
  из структуры напрямую, DXF оставить как отдельный экспорт в САПР.
