# Чистый контур в дипломном проекте: отчёт автору clean-contour

Проект — генерация векторных чертежей фасадов по плану дома и тексту (ВКР ИТМО, Python +
PyTorch, смотрелка — FastAPI и обычный JS без сборки). Кода — около 25 тыс. строк Python и 1,2
тыс. строк JS; базы данных и ORM нет: сущности живут в JSON-файлах (прогон, ответ модели,
отметка проверки глазами, копия задачи GitHub). Правила и навык взяты из
github.com/blurman-ai/clean-contour на коммите `f54f6d7` (Apache 2.0), задачи gf#291 и gf#293.

## Что взяли и как встроили

- `docs/clean-contour.md` и навык `clean-contour-check` — копиями без правок; поправить карточку
  мы договорились только у вас в репозитории и скопировать заново.
- Когда проверять — три точки в наших правилах разработки: перед починкой бага — по чинимому
  файлу; перед PR, который закрывает задачу, — по своему диффу (`dirty` в диффе чинится в том же
  PR, вне диффа — строкой в задаче); по слову хозяина «гигиена <область>» — по области.
- Кому какие карточки — по вашему экзамену 03.11 (DeepSeek flash): C1, C3, C6, C7, C9, C11, C12,
  C15 — дешёвой модели (у нас Claude Haiku), C2, C4, C5, C8, C10, C13, C14 — Sonnet; спорное и
  каждый `dirty` дешёвой модели перепроверяет основная сессия (Opus), потому что Haiku ваш экзамен
  не сдавала.
- Совпавшие с нашими правилами принципы оставили как были: enum вместо строк (п. 12, C9),
  «у проверки есть случай, на котором она падает» (п. 11), три неудачные попытки — стоп.

## Как шла гигиена

1. Первая гигиена (gf#291) — `genfacade/`, `tools/`, JS смотрелки; три субагента, спорное —
   основной сессией.
2. Добивка (gf#293) — сторож команд агента `.agents/guards/guard.py` и хук.
3. Починка группами, у каждой правки — проверка, которую мы видели красной на дефекте.
4. Повторная гигиена после первого круга — теми же карточками по всему коду сразу.
5. Второй круг починки и последняя гигиена.

## Примеры: dirty → clean

**Отказ текстом → кодом из списка (C15, п. 6, 17).** Было: сервер отдавал строку «код: текст»,
страница показывала `detail` как есть или подставляла своё «ошибка сервера».

```python
REFUSALS = {PlanError: "план отклонён", ModelError: "модель не ответила"}
raise HTTPException(400, f"{pipeline.REFUSALS[type(e)]}: {e}") from e
```
```js
if (!res.ok) throw Object.assign(new Error(errorText(data.detail)), { detail: data.detail });
function errorText(detail) { if (!Array.isArray(detail)) return detail ?? "ошибка сервера"; … }
```

Стало: один список `Refusal(StrEnum)` и `REFUSAL_TEXT` с текстом к каждому коду, исключение
`Refused(code, detail)`; у отказа модели — свой код на причину (нет годного ответа, нет модели,
чужой словарь, дом не по силам) вместо одного «модель не ответила». Ответ смотрелки, `meta.json`
прогона и сохранённый ответ модели — один вид `{code, text, detail}`. Страница своих кодов не
держит:

```python
raise HTTPException(400, e.record())   # {"code": "plan_rejected", "text": "план отклонён", "detail": "…"}
```
```js
if (!res.ok) throw await refusedFrom(res);   // static/refusal.js: текст — из ответа
```

TypeScript и сгенерированного контракта у нас нет, поэтому «таблица code → text, проверенная
компилятором» (п. 17) заменена так: текст отдаёт сервер, тест требует текст у каждого члена
`Refusal`, а статический тест — что в JS нет ни кодов, ни текстов отказов и `detail` не
подменяется своим значением.

**Итог от порядка ответов (C13, п. 14).** «Не годен» и причина на странице проверки уходили двумя
запросами, причина бралась из ещё не подтверждённой отметки. Воспроизвели в браузере (Playwright,
ответ на первый PUT задержан на 1,5 с внутри страницы): старый код сохранил `"why": ""`, новый —
`"why": "окна вразнобой"`. Стало: отметки одного места — очередью (`serial(key, task)`), причина —
с последним выбором пользователя. Редактор запроса — только для чтения, пока идёт прогон: после
ответа он перерисовывался из ответа сервера, и набранное за это время пропадало.

**Одно состояние, посчитанное дважды, — дыра в стороже (C5).** «Есть ли в команде
`gh pr create`» сторож считал трижды: по строке, разрезанной регэкспом, и по `shlex` всей строки.
`gh pr create;ls` и `echo ok;gh pr create --fill` одна проверка видела, другая — нет, и тело PR
не проверялось. Стало: один разбор строки (`shlex` с `punctuation_chars`, `;` вплотную к слову —
разделитель) для всех сторожей; упавший сторож — отказ, а не падение всего разбора (C10).

**Отрицательная проверка вида (C8, п. 9).**

```python
sealed = [f for f in found if blind and f.external and f.kind is not OpeningKind.ENTRANCE]
```
```python
SEALED_IN_BLIND = frozenset({OpeningKind.WINDOW, OpeningKind.DOOR})
sealed = [f for f in found if blind and f.external and f.kind in SEALED_IN_BLIND]
# тест: SEALED_IN_BLIND | {ENTRANCE} == set(OpeningKind) — новый вид проёма не проскочит молча
```

**Нет строки — это состояние (C2).** Шаг прогона считался записанным, если его файл есть в
папке, — поэтому перед прогоном приходилось удалять файлы прошлого. Стало: шаги в `meta.json`
называет тот, кто их записал (`_steps(done)`).

**Объявлено без писателя (C14).** `GuidelineUse.SYNTHETIC, DERIVE, TRAIN` никто не читал: правило
свода с `use = ["synthetic"]` молча ничего не включало. Убраны — теперь такой конфиг не
загружается.

**Одно правило в двух регэкспах — PR закрыл бы чужую задачу (C5, второй круг).** Сторож тела PR и
проверка коммита искали «слово закрытия + ссылка на задачу» каждый своим регэкспом. Проверка
коммита ловила `fixes https://github.com/a/b/issues/5`, сторож PR — нет, а GitHub закрывает и по
ссылке. Стало: ссылка на задачу объявлена один раз, оба импортируют её.

**Всё или ничего в CI (C10, C4, C2, второй круг).** После мержа скрипт переоткрывает задачи, по
которым упали тесты, и сохраняет список упавших как базу для следующего прогона. База писалась до
цикла переоткрытия: сбой API на первой задаче — и остальные не переоткрылись бы никогда, потому
что в следующий раз их тесты уже «старые красные». Переоткрытие шло без чтения состояния (открыло
бы закрытую «не будем делать»), а нет базы — все красные считались новыми. Стало: база — после
всех задач, `reopen()` читает задачу, неизвестная база — комментарий без переоткрытия (п. 7).

## Где карточки ошиблись

- **C7 у дешёвой модели — разбор объявленного протокола.** 7 мест `train/constraints.py:145–159`
  Haiku сочла dirty: вид элемента берётся из токена по префиксу `tokens.PREFIX`. Это объявленный
  протокол словаря, просто разобранный второй раз вне модуля-объявителя. «Не считается» говорит
  только о модуле, где префикс объявлен.
- **C7 на внешних данных без поля вида.** У BuildingNet категория дома есть только в имени модели,
  у PDF-листов Solar Decathlon вид листа — только в тексте страницы. Haiku отметила их dirty; поля
  вида там нет и не будет — это разбор чужого формата. Не хватает исключения «внешний источник, где
  вид задан только меткой; префиксы объявлены в конфиге».
- **C7/C2 на стаб модели.** Стаб шага «текст → параметры дома» ищет стиль по слову в тексте —
  ровно то, что делает модель, которую он заменяет.
- **C14 на объявленном спекой.** Члены enum, которых требует спека (11 классов CMP, угловое и
  ленточное окно, источники данных), но писатель которых — будущая задача, карточка считает
  dirty. Мы вели их как unclear с причиной «требование спеки, задача такая-то». Не хватает пункта
  «объявлено требованием, писатель запланирован».
- **C2 на «закрыто по умолчанию».** Нет журнала квитанций — push запрещён. Карточка видит «нет
  строки — состояние»; на деле это отказ с текстом «нет квитанции», то есть п. 7, а не нарушение.
- **C1 на шаблоне SDD.** Таблица статусов требований переносит вердикты из записей прогонов
  (`req_status.py --write`). Карточка видит «состояние из журнала». Это устройство нашего шаблона:
  таблица — хранилище, записи — свидетельства, перенос — писатель.
- **Полнота от запуска к запуску.** См. «Цифры»: Sonnet по тем же карточкам и файлам нашёл 0 и 12
  dirty в `tools/` в двух проходах. Для гигиены по области один проход — не гарантия.

## Что не подошло проекту

- Нет базы данных и ORM: ограничение БД из того же списка, миграция на копии рабочей базы,
  транзакция записи вместе с данными перехода — неприменимы. Состояние в JSON-файле; перенос
  старых данных сделан один раз скриптом, который удаляется вместе с задачей.
- Нет рабочего контура и прода: страж переходов «сначала пишет в журнал, потом отказывает»,
  тревоги на строку журнала — не к чему подключить.
- Нет пакетных границ и долгоживущих сущностей с таблицей переходов: реестр полей
  `status`/`state` и контракт импорта (п. 5, 10) не завели — таких полей в коде нет, кроме
  состояний задач GitHub, которые принадлежат GitHub.
- Нет TypeScript и сгенерированного контракта API — замену для п. 17 см. выше.
- Экзамен карточек на Haiku (exam из вашего репозитория, 600 вызовов) не запускали: ждёт решения хозяина.
