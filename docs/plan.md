# Генерация векторных чертежей фасадов по плану дома и описанию — план работы

Черновик для согласования с научными руководителями · 2026-09-28

Документ сводит в одно место всё, что выяснено за сентябрь: постановку после
переписки 28.09, разбор кода GenPlan и Facades-3D, обзор литературы, данные
и метрики. Цель — договориться о теме, новизне, методе и порядке работы.
Всё, что здесь предлагается впервые, помечено как **предложение**.

---

## Коротко

- **Что делаем.** Модуль, который по векторному плану дома и текстовому описанию
  строит **четыре согласованных фасада** в виде векторного чертежа (SVG) в цвете.
  Типы домов — коттеджи и многоквартирные, тип задаётся в тексте.
- **Где встаёт.** После GenPlan: GenPlan даёт план, модуль — фасады. Позже фасады
  могут идти в 3D-конвертер вместо нынешнего правила.
- **Менять генерацию GenPlan не нужно.** Окна в GenPlan не генерируются, а выводятся
  из разрывов в стенах. Режим «без референсов» делается заделкой разрывов
  в нашем препроцессоре. Подробно — раздел 4.
- **Главная идея метода (предложение).** Общие параметры дома (этажность,
  высоты, крыша, материалы) задаются один раз на весь дом, а элементы
  генерируются по сторонам. Тогда углы сходятся по построению, а не «если
  повезёт». Модель генерирует фасад как последовательность элементов
  «класс + прямоугольник», SVG получается из неё детерминированно.
- **Новизна** — в сочетании: фасад **по плану и тексту**, **векторный** выход,
  **четыре согласованные стороны**, проверяемые метрики структуры и соответствия
  плану. Ближайшие — ShellMaker (ECCV 2026, 3D-оболочка по стенам с проёмами
  и тексту) и коммерческий ArchyBase (фасады по плану, метод закрыт). Раздел 3.

## 1. Тема и постановка

**Тема по ТЗ:** «Разработка метода генерации векторных чертежей фасадов зданий».
Предлагаемое уточнение: *генерация согласованных векторных чертежей фасадов
здания по плану и текстовому описанию*.

```
вход:   текстовое описание дома
        + векторный план (стены, окна, двери; один этаж; в пикселях)
выход:  четыре фасада — векторный чертёж (SVG) в цвете
        + машиночитаемое описание фасадов (JSON) для 3D и проверок
типы:   коттеджи (план от GenPlan) и многоквартирные (план от коллег),
        тип задаётся в тексте
режимы: с референсами — окна и двери заданы планом, модуль достраивает остальное;
        без референсов — на плане глухой объём, проёмы ставит модуль
```

Режимы — требование Егора: так модуль встаёт в GenPlan отдельным сервисом.

**Сейчас вне работы** (решено 28.09, вернёмся после фасадов): разрезы,
3D-модель и BIM, фотореалистичные текстуры. «В цвете» на первом этапе —
цвет и материал элемента из фиксированной библиотеки (кирпич, штукатурка,
сайдинг, дерево, металлочерепица и т. п.), а не сгенерированная текстура.

**Ориентир по виду результата** — эскизный проект ИЖС, который мы обсуждали:
четыре фасада «в осях», с отметками уровней.

|---|---|---|
| **GenPlan** | текст → план (SDXL без дообучения + white loss) → векторизация в прямоугольники → 3D. Окна и двери — это разрывы в стенах, которые правило объявляет проёмами. ## 3. Новизна

**Ближайшие работы** — искали специально «фасад по плану», «фасады по контуру
здания», «план + текст → экстерьер», векторные фасады; по-английски и по-русски:

| Работа | Что делает | Чем отличается от нашей задачи |
|---|---|---|
| **ShellMaker** (Xu, Aliaga, ECCV 2026) | стены с заданными проёмами + текст стиля → 3D-оболочка дома с материалами и параметрической крышей | проёмы только принимает, не ставит; фасад — единая оболочка, этажей не различает (авторы пишут это в ограничениях); выход — 3D-меш, чертежей нет |
| **ArchyBase** (коммерческий сервис, 2026) | план (картинка, PDF, DXF) → четыре фасада, экспорт в SVG и DXF | метод не опубликован, метрик нет; текст — необязательная заметка |
| **GeoTexBuild** (arXiv 2025) | контур здания + стиль → 3D-модель | проёмов на входе нет, согласованность окон между сторонами не гарантируется, выход — меш |
| **Text2BIM** (J. Computing in Civil Engineering) | текст → BIM через LLM-агентов | плана на входе нет; авторы сами называют разумную расстановку проёмов трудной задачей для LLM |
| **FaçAID**, **Pro-DG** | структура одного фасада: разбор фото в грамматику, растровая генерация по иерархии | один фасад, без плана, без вектора, без текста |
| **HouseCrafter**, **Plan2Scene** | план → 3D-сцена | только интерьеры |

Свежий обзор по генеративному ИИ в проектировании фасадов (Building and
Environment, 2026) фиксирует, что в области «image-based data type dominates
both model input and output». Ни одной научной работы, где по плану строятся
**векторные** фасады, мы не нашли.

**Что заявлять нельзя:**

- «первыми генерируем фасады по плану» — ArchyBase делает четыре фасада по плану,
  пусть и без опубликованного метода;
- «первыми учим структуру фасада» — FaçAID;
- «первыми требуем регулярность» — Beyond Segmentation (для разбора фото)
  и GSDiff (для векторных планов);
- «первыми достраиваем экстерьер по стенам с проёмами и тексту» — ShellMaker, в 3D.

**Что остаётся нашим — сочетание, и каждая часть проверяема:**

1. **Векторные фасады по векторному плану и тексту** — воспроизводимый метод
   с оценкой; ближайшая научная работа (ShellMaker) выдаёт 3D-меш и этажей
   не различает.
2. **Четыре стороны, согласованные по построению** — этажи, карниз и крыша
   сходятся на углах; это измеряется.
3. **Два режима на одной модели** — модуль сам ставит проёмы или достраивает
   заданные; ShellMaker умеет только второе.
4. **Метрики:** согласованность с планом, соответствие описанию через парсер
   чертежа и разбор единственной опубликованной метрики регулярности фасада,
   у которой нашёлся вырожденный оптимум.

## 4. Нужно ли перестраивать GenPlan

Егор спрашивал, насколько трудоёмко вынести расстановку окон из генерации плана.
Ответ по открытому коду GenPlan (версия от 11.09.2026) и статье GenPlan
(VISAPP 2026):

1. **Генерация идёт на готовом SDXL без дообучения на планах.** Вклад GenPlan —
   white loss: поправка на первых шагах сэмплирования, которая выбеливает края
   картинки, плюс векторизация стен по углам. В коде и в статье нет ни обучения,
   ни датасета планов; если есть дообученная версия вне репозитория, мы её не видели.
2. **Окна нигде не генерируются как объекты.** SDXL рисует стены, разрывы
   в них возникают сами. Потом правило (`decorator`) объявляет проёмом любой
   промежуток между двумя соосными прямоугольниками стен: наружные — окна,
   самый узкий наружный — входная дверь, внутренние — двери.
3. **Значит, убрать окна из генерации — это не переобучение готовой модели**,
   а либо новый лосс против разрывов, либо впервые дообучать SDXL на датасете
   планов. Оба варианта дорогие и без гарантии. Заделать разрывы после генерации — дёшево.

| Вариант | Что меняется в GenPlan | Трудоёмкость | Что даёт |
|---|---|---|---|
| А. Ничего не менять | ничего | — | режим «с референсами»: окна = разрывы плана |
| Б. Заделать наружные разрывы, кроме входа | постобработка стен; можно делать на нашей стороне | малая | режим «без референсов» |
| В. Перестроить генерацию плана | дообучить или направить диффузию рисовать стены без разрывов | большая, результат не гарантирован | то же, что Б |
| Г. 3D-конвертер берёт окна из фасадов | `create_3d` принимает окна по сторонам со своими высотами; этажность | средняя для одного этажа, большая с этажами | 3D строится по нашим фасадам |

**Предложение:** генерацию GenPlan не трогать; режим «без референсов» делать
в препроцессоре фасадного модуля (вариант Б). Доработка GenPlan понадобится
только для обратной связи в 3D (вариант Г) — это работа вместе с Егором после
фасадов.

По ходу нашлось два мелких бага GenPlan, к фасадам не относятся, но стоит
знать:

- если две параллельные стены совпадают по протяжённости (противоположные стены
  прямоугольного дома), правило объявляет всё пространство между ними «проёмом».
  Воспроизведено на синтетической коробке из четырёх стен;
- в ветке SDXL с `--control_image` картинка-условие в сэмплирование не передаётся,
  так что условие по контуру фундамента не действует.

## 5. Метод (предложение)

### 5.1. Схема

```
текст ──► разбор описания ──► спецификация дома
                               (тип, этажность, высоты, крыша, материалы, стиль)
                                         │
план (SVG) ──► препроцессор ──► стороны дома: длина, проёмы, запретные зоны
                                         │
                                         ▼
                         генератор элементов фасада (по сторонам,
                          с общими параметрами дома)
                                         │
                                         ▼
                   привязка к сетке этажей и осей ─► валидатор
                                         │
                                         ▼
                   сборка: 4 фасада в SVG с отметками + JSON
```

### 5.2. Препроцессор плана

План GenPlan — это SVG из прямоугольников в пикселях; класс задан цветом,
стены перекрываются, наружный контур не помечен. Препроцессор:

- сливает перекрывающиеся стены и находит наружный контур;
- режет контур на стороны и проецирует на каждую проёмы (позиция и ширина вдоль стены);
- отмечает **запретные зоны** — места, где к наружной стене примыкает
  внутренняя: окно туда ставить нельзя (это ровно дефект «стена приходит в окно»);
- переводит пиксели в метры через заданную высоту стены или ширину входной двери;
- для режима «без референсов» заделывает наружные разрывы, кроме входа.

Внутри модуля план хранится в своём формате, не привязанном к GenPlan: для
многоквартирных планы придут от других коллег, и понадобится ещё один адаптер.

### 5.3. Представление фасада

Два уровня, чтобы четыре стороны сходились по построению:

- **Дом целиком:** число этажей и их высоты, отметка карниза, тип и уклон
  крыши, направление конька, материалы по классам элементов.
- **Сторона:** список элементов «класс + прямоугольник в метрах»: окна, двери,
  балконы, карнизы, подоконники, декор. Классы берутся из разметки CMP
  (12 классов), к ним добавляются классы для коттеджей.

Крыша и фронтон — не прямоугольники, поэтому они задаются параметрами дома,
а их силуэт на каждой стороне вычисляется геометрически: по контуру плана и
направлению конька получается фронтон или скат. Это закрывает главный недостаток
прямоугольного представления для коттеджей.

За основу берётся представление Facades-3D (элемент = класс + прямоугольник,
сетка этажей и пролётов) — оно совпадает с форматом разметки CMP.

### 5.4. Генератор

Модель генерирует элементы стороны последовательностью токенов
(«класс, x, y, ширина, высота» на квантованной сетке). Условия: спецификация
дома, описание стороны из плана, текст. Два режима отличаются только тем,
что подаётся на вход: в режиме «с референсами» горизонтальные позиции проёмов
заданы, модель достраивает вертикаль, этажи и декор.

Кандидаты архитектуры, по ТЗ сравниваются между собой:

1. **Дообученная LLM** (QLoRA на открытой кодовой модели), которая печатает
   элементы в компактном текстовом формате. В лаборатории уже есть рецепт
   дообучения LLM на SVG (Text2SVG). Быстрее всего заведётся на малом объёме
   реальных данных.
2. **Свой компактный трансформер** с предобучением на синтетике и дообучением
   на реальных данных. Структура под контролем, модель маленькая.
3. **Диффузия над множеством элементов** с графом отношений между ними
   (в духе LayoutDM, CVPR 2023, для графических макетов и GSDiff для планировок) —
   вариант «на основе графов», который требует ТЗ.

Разбор текста в спецификацию дома — отдельный шаг, который проверяется сам
по себе. Это заодно закрывает пункт ТЗ про условную генерацию по параметрам
(этажность, типы элементов): параметры можно задать и без текста.

### 5.5. Постобработка и вывод

- **Привязка к сетке:** элементы выравниваются по линиям этажей и вертикальным
  осям, чтобы соседние окна получили одинаковые координаты.
- **Валидатор:** элементы внутри контура стены, проёмы не пересекаются,
  окно не попадает в запретную зону, проёмы совпадают с планом (в режиме
  «с референсами»), на углах совпадают высоты и линия крыши.
- **Вывод:** SVG с классом у каждого элемента, лист из четырёх фасадов
  с отметками уровней и JSON с тем же содержимым — для 3D и для метрик.

Отсюда схема: синтетика даёт пары и объём, реальные данные — проверку

| Источник | Что это | Для чего | Ограничения |

**Текстовые описания** в этих данных отсутствуют. Их синтезируем из разметки
по шаблонам (этажность, число окон, крыша, материалы — извлекаются точно),
перефразируем LLM, а проверяем на описаниях, написанных вручную, чтобы модель
не выучила шаблон.

## 7. Оценка

### Пять групп метрик из ТЗ и две наши

| Группа | Как считаем |
|---|---|
| 1. Визуальное сходство | FID/KID по растеризованным фасадам против растеризованной реальной разметки |
| 2. Корректность геометрии | валидатор: доля фасадов без нарушений и нарушения на фасад |
| 3. Корректность структуры | ошибка выравнивания окон по этажам и осям, стабильность шага этажей — относительно распределения реальных фасадов, а не идеальной решётки. SVD-метрика Beyond Segmentation — вспомогательной колонкой, у неё вырожденный оптимум (см. ниже) |
| 4. Разнообразие | попарное расстояние между образцами при одном условии, покрытие реального распределения |
| 5. Доля валидных документов | SVG парсится и проходит валидатор |
| **Согласованность с планом** | проёмы совпадают с планом, в запретных зонах окон нет, углы сходятся |
| **Соответствие описанию** | из текста — проверяемые требования («этажей 2», «крыша вальмовая»), проверка парсером чертежа. Выход векторный, поэтому проверка точная, а не через детектор |

**SVD-метрика.** Мы проверили единственную опубликованную метрику регулярности
фасада (Beyond Segmentation): идеальный счёт у неё получают и идеальная решётка,
и один прямоугольник, и пустая маска, а выбросить девять окон из десяти ей
выгоднее, чем выровнять их. Для оценки генерации в одиночку она не годится.
Это отдельный результат, пригодный для текста работы.

### Базовые подходы

1. **Правило GenPlan:** окна = разрывы плана, одна высота на дом.
2. **LLM без дообучения**, которой дают план и текст и просят SVG.
3. **Растр + векторизация:** диффузия рисует фасад, EvoVec переводит в вектор —
   исходная идея Егора, без знания о структуре.
4. **Процедурный генератор** (building_tools) со случайными параметрами под текст.

### Ablation

- представление: наш формат элементов против сырого SVG как текста;
- привязка к сетке: с ней и без неё;
- общие параметры дома против независимой генерации каждой стороны — это
  проверяет главную идею согласованности;
- предобучение на синтетике: с ним и без;
- условие по плану: с ним и без (модель, видящая только текст);
- архитектуры из 5.4 между собой.

## 9. Риски

- **Мало реальных парных данных.** Реальных пар «план → фасады» — десятки
  (Solar Decathlon). Основной объём — синтетика, и модель рискует выучить
  правила генератора. Смягчаем дообучением на реальных данных и тестом только
  на реальных.
- **Многоквартирные.** У CMP нет планов и четырёх сторон, формат планов
  коллег неизвестен. Для многоквартирных первая версия — генерация одной стороны.
- **Лицензии.** У GenPlan, Text2SVG и VGLib (EvoVec) в репозиториях нет лицензии,
  формально их код переиспользовать нельзя без письменного разрешения.
  У Facades-3D — MIT.
- **Конкуренция.** Группа Plocharski–Musialski публикуется по фасадам каждые
  несколько месяцев; их логичный следующий шаг — текст и вектор.
- **Дефекты входного плана.** Выход GenPlan бывает с дефектами; препроцессор
  должен их переживать или отбраковывать план.

## 10. Вопросы

1. **Рендеры коттеджей.** Откуда присланные 306 рендеров и можно ли использовать
   их в публикации? (Городского датасета «растр от векторных фасадов», как выяснилось
   29.09, нет.)
2. **Многоквартирные.** Кто из коллег делает планы и в каком формате? Есть ли пример?
3. **Идея согласованности.** Устраивает ли, что четыре стороны сходятся за счёт
   общих параметров дома, а не выучиваются моделью?
4. **Цвет.** На первом этапе — цвет и материал из библиотеки; текстуры позже. Так можно?
5. **GenPlan.** Согласны ли, что генерацию не трогаем, а режим «без референсов»
   делаем в фасадном модуле? И нет ли дообученной версии GenPlan, которой нет
   в открытом репозитории?
6. **Ресурсы и сроки.** Есть ли доступ к GPU? На какой воркшоп целимся
   и когда дедлайн?
7. **Примеры планов.** Можно ли получить 10–20 SVG-планов GenPlan на разных
   описаниях? Сейчас есть один пример, а препроцессору нужно разнообразие.
8. **Лицензии.** Можно ли получить разрешение на использование кода GenPlan,
   Text2SVG и VGLib (или добавить лицензию в репозитории)?
