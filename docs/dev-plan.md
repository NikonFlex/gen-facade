## Принцип

Сначала за 2–3 недели собрать весь конвейер: SVG-план + текст на входе, лист
фасадов на выходе. На шагах 1 и 4 вместо модели стоят стабы с её интерфейсом
*(хозяин 30.09, gf#60)*. Потом каждый шаг улучшаем отдельно. Модель встаёт на место
стаба, когда метрика уже считается; базовые подходы для сравнения — в evaluation.md.

Порядок режимов: конвейер — сразу в обоих режимах; модель, метрики
и первое демо Егору — сначала в режиме 2 (окна из плана), затем режим 1 на том же
представлении (decisions.md, 29.09 «порядок режимов»).

## Модули

Три группы: **конвейер** обрабатывает один запрос; **данные** готовят примеры
для обучения и теста; **оценка** проверяет и считает метрики. Всё связано типами
из `schema.py`: модули передают друг другу только эти объекты, и каждый объект
сохраняется в JSON.

### Конвейер — по модулю на шаг схемы

| Модуль | Шаг | Вход → выход | Кто работает | Спека |
|---|---|---|---|---|
| `schema.py` | — | `Request`, `Plan`, `Side`, `Opening`, `ForbiddenZone`, `HouseSpec`, `Roof`, `SideFacade`, `Element`, `MaterialZone`, `FacadeSheet` | — | все |
| `models/` | 1, 4 | текст → `HouseSpec`; стена + контекст → `SideFacade` | стаб → модель | generation, facade |
| `plan/` | 2 | SVG-план → `Plan`: стороны, проёмы, заделанные разрывы, запретные зоны, метры | код | plan-input |
| `unfold.py` | 3 | `HouseSpec` + длина стороны → пустая стена с силуэтом | код | facade |
| `snap.py`, `validate.py` | 5 | привязка к сетке этажей и осей; нарушения `Violation`; брак → заново — с моделью | код | generation, evaluation |
| `render/` | 6 | `FacadeSheet` → лист SVG + JSON + PNG-превью; SVG для трассы каждого шага | код | facade |
| `pipeline.py` | 1–6 | склейка шагов, режим `blind` / `with_openings`, запись трассы | код | task |

Шаг 7 (окна в 3D-конвертер GenPlan) — позже, вместе с Егором (integration.md).

У стаба и модели на шагах 1 и 4 один интерфейс (`models/stub.py`: `spec_model(text)`,
`layout_model(wall, ctx)`), поэтому модель заменяет стаб без правок остального кода.

## Трасса и смотрелка

Задача — gf#45. Цель — видеть глазами каждый шаг, а не только итог.

**Трасса.** Конвейер на каждом шаге сохраняет свой выход (specs/generation.md, п. 9):

```
outputs/runs/<id>/
  request.json   input_plan.svg   текст, режим (seed — с моделью); план как пришёл
  01_spec.json                    HouseSpec
  02_plan.json   02_plan.svg      стороны с номерами, заделанные разрывы, запретные зоны
  03_unfold.svg                   пустые силуэты стен
  04_layout.svg                   что поставили стаб или модель
  05_snapped.svg violations.json  после привязки к сетке, нарушения подсвечены
  06_sheet.svg   sheet.json       итоговый лист
  meta.json
```

SVG рисует `render/` — тот же код, что в тестах и на выходе. Смотрелка ничего не
считает: второй отрисовки, которая разойдётся с настоящей, нет; любой прошлый
прогон открывается без пересчёта; так же смотрим извлечённые дома BuildingNet
и CMP на этапе данных.

**Страница** — два экрана *(хозяин 30.09: прогон — на весь экран)*. Главная: дома
и вход — план (пример, загрузка SVG GenPlan, позже — нарисовать), текст, режим —
и история прогонов сеткой. Прогон — отдельный экран на всю ширину: сверху «назад»,
название и кнопки, ниже шаги 1 → 6 по порядку и чертёж; слои галочками
(оси, запретные зоны, нарушения, подписи классов); при наведении на элемент —
класс, материал, координаты, нарушенное правило. Сравнение двух прогонов рядом
(seed, правило против модели, режим 1 против режима 2). Галерея прогонов
и примеров датасета с метриками.

**Запуск:** `genfacade serve` → http://127.0.0.1:8000 (адрес и папки — `config/viewer.toml`).

**Реализация.** FastAPI + одна HTML-страница с небольшим JS; SVG отдаёт сервер.
Streamlit и Gradio плохо подходят под интерактивный SVG. Перед кодом —
поиск готового (NiceGUI, Streamlit с canvas, веб-редакторы планов), выбор
сообщается хозяину. Запуск локальный, с удалённой машины — через проброс порта.

**Редактор плана** — после этапа 1, минимальный: сетка в метрах, контур кликами,
окна и двери кликом по стене. Выдаёт SVG **в формате GenPlan** (стены
полигонами, проёмы разрывами), чтобы нарисованный план шёл через настоящий
препроцессор.

Смотрелка — инструмент, не часть диплома: держим тонкой, тесты — только что
сервер поднимается и отдаёт трассу.

## Как проверяем

1. **Критерии приёмки → тесты.** Каждый пункт «Критериев приёмки» спеки — тест
   в `tests/acceptance/` со ссылкой на спеку.
2. **Сломать и проверить.** Каждый тест один раз проверяется на сломанном коде.
3. **Глазами.** Трасса и смотрелка после каждого изменения отрисовки или раскладки.
4. **Прогоны сравниваем по таблице метрик**, а не по памяти; `meta.json` у каждого.
5. **CI:** `ruff`, `pytest` на CPU, `spec_check`, самопроверка `backlog.py`.
   Обучение и платные API в CI не ходят.

## Процесс на задачу

Задача → ветка `NN-имя` → тесты по критериям спеки → код → `ruff` и `pytest`
→ трасса глазами → PR с `Closes #NN` → хозяин проверяет → merge. С первого кода
работаем через ветки и PR (CLAUDE.md, правило 5); документацию, как и раньше,
можно коммитить в main.
