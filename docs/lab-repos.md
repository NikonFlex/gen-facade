## Facades-3D — разобран по коду

https://github.com/CTLab-ITMO/Facades-3D · Python · **MIT, © 2026 ITMO CT Lab** ·
создан 2026-06-30, обновлён 2026-09-13

Разобран 2026-09-25. Всё в этом разделе — `[проверено: код]`, если не указано иное.
Лицензия MIT проверена в файле LICENSE — переиспользовать можно.

### Пайплайн целиком

```
mass-модель (.obj)
  └─ walls_clustering.py        разбиение на стены, габариты в метрах
       └─ facade_semantic_map_gen_v2.py
            render_facade_segmentation(width_m, height_m, pixels_per_meter, seed)
            ├─ ПРОЦЕДУРНАЯ генерация структуры фасада (правила + random)
            └─ растеризация структуры в PNG-сегментацию
                 └─ gen_wall.py  диффузия по сегментации
                      SD 1.4 + ControlNet-seg + LoRA buildingface + IP-Adapter
                           └─ trellis_image_to_facade.py → 3D-меш с текстурой
```

Модели (`src/default_configs.py:15-23`):

| роль | модель |
|---|---|
| база | `CompVis/stable-diffusion-v1-4` |
| ControlNet | `lllyasviel/sd-controlnet-seg` |
| LoRA | `./aux/buildingface.safetensors` (лежит в репозитории) |
| референс стиля | `h94/IP-Adapter`, `ip-adapter_sd15.bin` |
| 3D | `microsoft/TRELLIS-image-large` |

Промпт по умолчанию: `"modern style architecture, urban house"`,
негативный — `"old, dark, distorted"`.

В `example_data/` лежат `cube.obj` и `parallelepiped_grid.obj` — ровно те «кубики
и параллелепипеды», о которых говорил Егор.

### Формальное представление фасада у них уже есть

`src/facade_semantic_map_gen_v2.py:159-238` — параметрическое описание фасада
в метрах, frozen-датаклассы:

- **`BuildingGrid`** — `width_m`, `height_m`, `ground_floor_height_m`,
  `upper_floor_height_m`, `upper_floor_count`, `bay_count`, `bay_width_m`,
  `floor_zone_height_m`, `roof_offset_m`. То есть сетка этажей и вертикальных
  пролётов задана явно.
- **`FacadeGeometry`** — около 25 параметров: размеры и положения окон первого
  и верхних этажей, дверей, балконных дверей, отливов, сандриков, боковых наличников,
  межэтажных тяг, венчающего карниза.
- **`Element`** — `class_name` плюс `x0_m, y0_m, x1_m, y1_m`.
  **Axis-aligned прямоугольник с классом.**
- **`FloorConcept`** — набор элементов этажа плюс тип завершения.
- **`UpperFloorStyle`** — флаги наличия сандриков, наличников, тип завершения.

Классы (`ClassName`, строки 12-20): `facade_wall`, `window`, `door`, `cornice`,
`sill`, `balcony`, `molding` — **подмножество 12 классов CMP**.

**`Element` структурно совпадает с аннотацией CMP:** класс плюс axis-aligned
прямоугольник. Это очень удачно — см. вывод ниже.

### Три дыры, в которых живёт диплом

**1. Структура не управляется описанием.** `gen_wall.py:280` вызывает
`render_facade_segmentation(width_m, height_m, pixels_per_meter, seed)` —
и всё. **Промпта там нет.** Текстовое описание уходит только в диффузию, то есть
влияет на внешний вид, но не на раскладку. Число этажей и пролётов вычисляется
из габаритов стены, остальное сэмплируется от `seed`.

По контракту диплома вход — описание, и оно должно задавать именно структуру
(«пять этажей, балконы на втором и третьем»). Этого нет.

**2. Структура не выучена, а прописана правилами.** `generate_facade_structure`
(строка 748) — процедурный сэмплер на `random.Random`, 1301 строка правил.
Разнообразие ограничено тем, что заложили руками. Повторяемость этажей тоже
захардкожена: генерируется несколько «концептов» этажа, дальше они циклически
переиспользуются (строки ~774-785).

Это ровно та критика процедурных методов, которая стоит в ТЗ Валерии:
«процедурные методы требуют заранее заданных правил и ограничивают разнообразие
результатов».

**3. Структура выбрасывается.** Список `Element` существует в памяти, растеризуется
в PNG и на этом заканчивается. Поиск по всему репозиторию
(`svg|vector(iz|ise)|potrace|cairo|dxf|cad`, исключая `third_party/`) даёт
**ноль совпадений**. Векторного выхода нет ни в каком виде.

### Что это значит для диплома

**Хорошая новость.** Не нужно поднимать ни диффузию, ни ControlNet, ни 3D —
всё готово и под MIT. И формальное представление фасада, которого требует ТЗ,
уже спроектировано, можно брать `BuildingGrid` + `Element` за основу
вместо изобретения своего.

**Плохая новость.** Превратить их `Element` в SVG — это полсотни строк.
Само по себе это не диплом.

**Где тогда вклад.** В том, чтобы заменить пункты 1 и 2:
**выучить структуру фасада из данных и подчинить её описанию**, вместо того чтобы
сэмплировать по написанным вручную правилам.

И вот здесь всё сходится: их `Element` — это класс плюс axis-aligned прямоугольник,
и разметка CMP Facade — ровно то же самое, 51 769 таких прямоугольников
(см. [datasets.md](datasets.md)). То есть модель, обученная на CMP, выдаёт объекты
того же типа, которым оперирует Facades-3D. Такой модуль:

- даёт векторный чертёж напрямую (список прямоугольников с классами → SVG);
- встаёт в их пайплайн вместо процедурного генератора, и ControlNet с TRELLIS
  продолжают работать без изменений;
- закрывает ровно ту претензию к процедурным методам, которая сформулирована в ТЗ.

### Палитра совпадает с CMP побайтово `[проверено: свой анализ]`

Словарь `COLORS` (строки 26-34) сверен с палитрой масок CMP Facade — **совпадение
7 из 7 классов, точное**:

| Facades-3D | RGB | класс CMP |
|---|---|---|
| facade_wall | (0, 0, 255) | facade |
| window | (0, 85, 255) | window |
| door | (0, 170, 255) | door |
| cornice | (0, 255, 255) | cornice |
| sill | (85, 255, 170) | sill |
| balcony | (170, 255, 85) | balcony |
| molding | (255, 85, 0) | molding |

Facades-3D строит семантические карты **в палитре CMP**. Отсюда три следствия:

1. LoRA `buildingface.safetensors` почти наверняка обучалась на CMP или на данных
   в его палитре. `[не проверено]`
2. Модель, обученная на CMP, рендерится в ровно ту же палитру и подаётся
   в их ControlNet **без единой строчки конвертации**.
3. **Facades-3D использует только 7 классов из 12.** Не задействованы
   `blind`, `deco`, `pillar`, `shop` — а в CMP их 19 232 штуки, это 37% всей разметки
   (pillar 7168, blind 4425, deco 4070, shop 1769, см. [datasets.md](datasets.md)).
   Модель, обученная на полном CMP, способна порождать заметно более богатую
   структуру, чем их процедурный генератор. Это измеримое улучшение и хороший
   дополнительный аргумент новизны.

## Text2SVG — разобран по коду

https://github.com/CTLab-ITMO/Text2SVG · HEAD `b94145b`, последний push 2025-08-04 · ★6

Разобран агентом, ключевое перепроверено. **Лицензии нет** `[проверено: GitHub API]`.

### llm4svg — готовый рецепт baseline

Всего два скрипта, ~170 строк. `[из отчёта агента]`

- База: **Qwen2.5-Coder-32B-Instruct**, загрузка через `unsloth` с `load_in_4bit`,
  то есть фактически **QLoRA**
- LoRA: `r=128`, `alpha=32`, `use_rslora`, обучаются в том числе `embed_tokens`
  и `lm_head` — типовой приём, когда токены домена далеки от естественного языка
- Данные: `VectorGraphics/SVG_corpus_3M`, поля `caption` и `svg_contents`
- Формат примера — ChatML, **сырой SVG прямо в ответе ассистента**, без DSL
  и спецтокенов; лосс только на ответе
- `max_seq_length = 1024` — для фасада с десятками окон этого мало
- `lr=5e-5`, embedding lr `1e-5`, 1 эпоха, `adamw_8bit`

**`run_eval.py` метрик не содержит** — это демо-генерация одного примера
с захардкоженным промптом. Метрик генерации в репозитории нет нигде.

### svg-encoder — нам не подходит

Это **MLM-энкодер** на базе ModernBERT, генерировать не умеет. Кодирование —
чистая токенизация текста SVG переобученным BPE (~201k словарь), никакого
отдельного представления примитивов. `[из отчёта агента]`

### ⚠ Их препроцессинг уничтожает ровно то, что нам нужно

Самое важное из разбора. Корпус нормализуется так, что **все примитивы
превращаются в `<path>`**: `rect`, `circle`, `line`, `polygon` конвертируются
в пути, а при `cubic_only=True` даже прямые отрезки становятся кубическими
Безье. Затем SVGO с `convertShapeToPath` добивает остатки. `[из отчёта агента]`

Наш целевой формат — фасад как список axis-aligned `<rect>` с классом — их
пайплайну противоположен. Более того, **места под класс примитива**
(window / balcony / door) в их представлении нет вообще, только презентационные
атрибуты вроде `fill`.

Это неудобство, но и готовая формулировка отличия нашей работы в обзоре.

### captioning — каркас берём, содержимое нет

`caption_intern.py`, 153 строки. VLM — `OpenGVLab/InternVL3-2B`, SVG растеризуется
в **224×224**, промпт собирается случайно из 4 стилей × 4 фокусов × 5 длин. `[из отчёта агента]`

Для фасадов в текущем виде не годится: на 224×224 этажи и оконные оси не сосчитать,
2B-модель слабо считает объекты, выход — свободный текст без схемы.

**Вывод, важный для issue #13:** у CMP разметка по классам уже есть, поэтому
описания вида «пять этажей, восемь осей» надёжнее **синтезировать из аннотации
шаблоном**, а VLM оставить только на стилевые атрибуты. Дешевле, точнее, проверяемо.

### Что берём

1. Рецепт SFT из `run_training.py` целиком — как **baseline** «LLM печатает SVG
   как текст» для ablation против структурированного метода
2. Приёмы нормализации SVG: единая канва, целочисленные координаты,
   детерминированный порядок атрибутов
3. Каркас каптионера (батчинг, resume, JSONL)

### Чего не берём

`svg-encoder` (не генератор), препроцессинг «всё в cubic path» (антипаттерн для нас),
`run_eval.py` (метрик нет), кэпшны InternVL@224.

Все HF-артефакты (`VectorGraphics/*`) анонимно недоступны — нужен доступ
от лаборатории. `[из отчёта агента]`

## VGLib — библиотека векторной графики, в ней EvoVec

https://github.com/CTLab-ITMO/VGLib · Python · создан 2024-05-22, обновлён 2025-06-05 · ★6

«Библиотека методов машинного обучения по обработке и генерации векторной графики».
Поддержана НТИ, соглашение 70-2021-00187.

Содержит:

| Метод | Что делает |
|---|---|
| **EvoVec-Evolutionary-Image-Vectorization/** | эволюционная векторизация — **статья Егора** |
| VectorWeaver/ | безусловный генератор векторных изображений, двухстадийный трансформер |
| VectorNST/ | перенос стиля в векторной графике |
| CoverGAN/ | генератор векторных обложек альбомов |
| extended_recursive_memory_transformer/ | детекция плагиата чертежей, рекуррентный трансформер с памятью |

### ⚠ У VGLib нет лицензии

`[проверено: свой анализ клона, HEAD 7638701]`

Во всём репозитории единственный файл лицензии — `CoverGAN/LICENSE`, относящийся
к другому подпроекту. **У корня VGLib и у папки EvoVec собственной лицензии нет.**
В корне только `README.md`, `README_eng.md`, `.gitignore` и подпапки методов.

Юридически код без лицензии — это «все права сохранены»: переиспользовать,
модифицировать и публиковать производную работу нельзя без явного разрешения.
Указание на финансирование НТИ (соглашение 70-2021-00187) в README лицензией
не является.

Для диплома это блокер, а не формальность: если метод строится поверх EvoVec,
а результат выкладывается в открытый репозиторий и идёт в статью, разрешение
нужно получить письменно. Контраст: у Facades-3D лицензия MIT, там вопросов нет.

**Вот где лежит EvoVec** — искали отдельный репозиторий, а он подпапкой здесь.
Структура: `main.py`, `vectorize_by_algo.py`, `config.py`, `cache.py`,
`crossover/`, `mutations/`, `fitness/`, `dto/`, `utils/`, `test/`.

Отдельного внимания заслуживает **VectorWeaver** — трансформерный генератор векторной
графики. Для пути A это прямой методологический ориентир внутри своей же лаборатории.

## Выводы

1. **Свою диффузию поднимать не нужно** — Facades-3D уже генерирует растровые фасады
   с ControlNet и управлением стилем.
2. **Свой векторизатор писать не нужно** — EvoVec (VGLib) и LIVBOC готовы.
3. **Проблема отсутствия описаний решаема** — VLM-каптионинг в Text2SVG.
4. **Путь A не с нуля** — llm4svg, svg-encoder, VectorWeaver.
5. **Метрик векторной графики в лаборатории нет** — VecScore пустой. Это дырка,
   которую можно закрыть своим вкладом.

Главный риск теперь другой, чем казался: не «не хватит инструментов», а
**«всё уже сделано до меня, где моя новизна»**.

**Разбор Facades-3D по коду (25.09) этот риск снял.** Структура фасада у них
генерируется процедурно по написанным вручную правилам, не зависит от текстового
описания и выбрасывается при растеризации. Векторного выхода нет нигде.
Вклад диплома — выучить структуру из данных и подчинить её описанию.
Формулировка новизны — история; актуальная — docs/plan.md §3 (gf#3).
